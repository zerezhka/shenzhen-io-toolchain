# Known Gaps

What the toolchain is currently missing, verified against the local game
install and the reference implementations. See
[reference-simulators.md](reference-simulators.md) for the external-reference
comparison and [undocumented-instructions.md](undocumented-instructions.md)
for the `gen`/`@` spec.

## 1. Simulator: `gen` is parsed but not executable

- `Sio.Assembler` accepts `gen` (`src/Sio.Assembler/Parse/Parser.cs`).
- `Sio.Simulator` has **no implementation**: no `Gen.cs` in
  `src/Sio.Simulator/Isa/Instructions/`, not registered in
  `InstructionRegistry`, absent from `InstructionSetManifest.AllInstructions`
  (which claims to be the "single source of truth" but lists only the 15
  documented instructions).
- Result: a program using `gen` parses fine, then `StepEngine` throws
  `Unsupported instruction: gen` at runtime.
- Fix is fully specified: `gen P X Y` ≡ `mov 100 P` / `slp X` / `mov 0 P` /
  `slp Y` (see the spec doc).

## 2. Simulator: `@` once-only prefix is parsed but not executable

- The C# parser treats `@` as a valid instruction name; the simulator has no
  handler and no "execute once" state anywhere (`grep -rn Once src/Sio.Simulator`
  finds nothing), so it throws the same `Unsupported instruction` error.
- Semantics: prefix that makes the marked instruction execute only on the
  first pass. Modeling note: it is a *prefix* (like `+`/`-`), so it may fit
  better as a flag on the instruction model than as an `IInstruction`.

## 3. Zig toolchain: no simulator yet

The Zig rewrite (`zig/src/`) currently covers tokenizer, parser, extension
preprocessor, emitter, and the `assemble` command. Parsing covers all 16
mnemonics plus `@`. There is no execution engine; the C# simulator remains the
only one (see [zig-rewrite.md](zig-rewrite.md)).

## 4. No original game test data — for any level

The game (local install) has **45 puzzles**
(`originalgamefilessteam/Content/descriptions.en/` has 45 entries). The
verification waveforms you see in-game are **generated by game code at
runtime and are not shipped in any extractable form** — so we have original
input/expected-output test vectors for **zero** of the 45 levels.

Why extraction is not possible (verified against the local install):

1. **No data files exist.** `Content/` holds only assets — shaders, fonts,
   music, textures, the manuals, `descriptions.*`/`messages.*` text;
   `PackedContent/` is just fonts. There is no puzzle-definition file format
   on disk (MoonSharp/Lua ships only for the sandbox/custom-puzzle path).
2. **Puzzles are compiled C# inside `Shenzhen.exe`** (Mono/.NET PE; class
   names like `Puzzle`, `Puzzles`, `PuzzleDescriptionItem` are visible in the
   binary). Test inputs are produced by per-puzzle *generator code*, and
   expected outputs are *computed* from those inputs — the tests are
   functions, not data.
3. **The binary is obfuscated** with Eazfuscator.NET (~10,000 `#=q…`
   identifiers), so decompiling yields symbol soup; recovering each puzzle's
   generator is a reverse-engineering project, not an extraction.
4. **Inputs vary per verification run** (seeded/randomized generation), so
   even a runtime capture (memory hook) yields one random sample, not the
   spec.
5. Anything captured would still be original game content and must not be
   redistributed ([local-original-assets.md](local-original-assets.md)).

What we have instead (proxies, not originals):

| Source | Coverage | What it validates |
|---|---|---|
| Community solutions (483 chips, `third_party/`) | most levels | **parse/assemble only** — no I/O behavior (see [validation-results.md](validation-results.md)) |
| Verification-tab screenshots (76 usable PNGs, shiawasenahikari set) | all 41 campaign levels + bonuses | one sampled run per level; binary/analog simple-I/O traces are pixel-extractable without OCR, XBus needs OCR or manual reading (see [community-test-data.md](community-test-data.md)) |
| Manual PDF Supplemental Data + level descriptions | ~10 levels reference the manual | **exact behavioral formulas** (e.g. amplifier's `AUDIO_OUT = (AUDIO_IN - 50) x 4 + 50`, unknown-device's x/y→power map) — expected outputs computable from inputs, clean-room |
| Save-file metrics (`[power-usage]`, `[lines-of-code]`) | every solved level | potential **simulation oracle**: re-simulating a solution must reproduce its recorded power usage — requires full multi-chip board simulation |
| Hand-written YAML tests (`examples/us1–us3`, `examples/multi-chip`) | synthetic examples only | simulator behavior, but not against any real game level |
| Level descriptions (`descriptions.en/*.txt`) | all 45 levels | human-readable requirements; for fixed-output levels they confirm the screenshot waveform *is* the spec ("fixed, repeating signals") |

Realistic paths to per-level test data, in increasing order of effort
(assessed in detail in [community-test-data.md](community-test-data.md)):

1. Hand-transcribe the binary-waveform levels (camera, pulse generator,
   animated sign) from the shiawasenahikari screenshots — readable today, no
   tooling.
2. Write a pixel-extraction script for the shiawasenahikari set (uniform
   1920×1080, orange polylines on dark grid) to bulk-extract binary/analog
   traces; only XBus levels need OCR. Where the manual publishes the
   input→output rule (~10 levels), compute expected outputs instead of
   transcribing them.
3. Use save-file `[power-usage]` as a cheap regression oracle once multi-chip
   simulation works.
4. The game logic is C#/Mono, but `Shenzhen.exe` is Eazfuscator-obfuscated and
   stores tests as generator *functions*, not data — see the time-boxed
   investigation in [deobfuscation-attempt.md](deobfuscation-attempt.md). Do
   **not** redistribute anything extracted this way
   (see [local-original-assets.md](local-original-assets.md)).

## Prior art: declarative test harness (what makes this project different)

A web survey (2026-06-12) of the public Shenzhen I/O ecosystem found no other
project with a **declarative, data-driven test format** for verifying Shenzhen
assembly, nor any attempt to **reconstruct the game's per-level verification
data**. What exists elsewhere:

- **Simulators / emulators** verify with code-level testbenches or ad-hoc unit
  tests baked into the implementation, not portable test definitions:
  [nielseneli/shenzhen-io](https://github.com/nielseneli/shenzhen-io) (Verilog
  + Python), [a2435191/shenzhen-lean](https://github.com/a2435191/shenzhen-lean)
  (Lean 4), anthonywritescode/shenzhen-io-sim (Python).
- **Assemblers** ship example `.asm` files but no behavioral harness:
  [omaskery/shenzhen.io-assembler](https://github.com/omaskery/shenzhen.io-assembler).
- **Solution collections, solitaire solvers, mods** — unrelated to program
  verification (see [reference-simulators.md](reference-simulators.md) and
  [deobfuscation-attempt.md](deobfuscation-attempt.md)).

This project's [test format](test-format.md) — input streams, expected output
events, cycle-exact vs. order-only modes, port→stream mappings authored as
YAML/JSON — appears to be the only public toolchain treating Shenzhen test
cases as portable data you can author and reproduce outside the game.

Caveats: web search is US-indexed and cannot prove a negative (a private repo
or non-indexed forum post may exist). "Unique" refers specifically to the
*declarative-harness + reconstruction* combination — many people have run
Shenzhen assembly against *some* tests; what is unrepresented elsewhere is the
data-driven format and the goal of reproducing the game's level verification.
