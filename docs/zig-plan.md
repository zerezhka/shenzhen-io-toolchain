# План переписывания на Zig — для тех, кто не писал компиляторы

Это **учебный план** (companion к [zig-rewrite.md](zig-rewrite.md), где про
«что и зачем»). Здесь — «как», маленькими шагами, с объяснением понятий и
ссылками. Цель: чтобы можно было идти по шагам, даже если слова «лексер» и «AST»
ты видишь впервые.

---

## 0. Сначала главное: мы пишем НЕ «настоящий компилятор»

Когда говорят «компилятор», обычно представляют что-то огромное (как `gcc`),
которое превращает C++ в машинный код с кучей оптимизаций. У нас **сильно проще**.
У нас две маленькие программы:

1. **Ассемблер** — берёт твой `.asm` (с удобствами: комментарии, `const`,
   `alias`, `include`) и превращает его в «ванильный» asm, который понимает игра.
   По сути — текст-в-текст с проверками.
2. **Симулятор** — берёт asm и **выполняет** его по тактам, как маленький
   процессор, чтобы можно было отладить программу вне игры.

Ассемблер — это маленький подвид компилятора. Симулятор — это **интерпретатор /
виртуальная машина**. Обе вещи используют один и тот же первый этап — разбор
текста на «слова». С него и начнём.

📖 Понятия одним абзацем:
- **Язык ассемблера (assembly)** — текстовые команды, почти 1-в-1 с тем, что
  делает процессор. — [ru](https://ru.wikipedia.org/wiki/Язык_ассемблера) ·
  [en](https://en.wikipedia.org/wiki/Assembly_language)
- **Ассемблер (программа)** — переводит assembly в машинный/целевой код.
  [en](https://en.wikipedia.org/wiki/Assembler_(computing))
- **Компилятор vs интерпретатор** — компилятор *переводит и сохраняет*,
  интерпретатор *читает и сразу выполняет*. —
  [компилятор](https://ru.wikipedia.org/wiki/Компилятор) ·
  [интерпретатор](https://ru.wikipedia.org/wiki/Интерпретатор)

## 1. Конвейер: из чего состоит наш «компилятор»

Любой компилятор/ассемблер — это **конвейер** (pipeline): текст проходит через
несколько этапов, на каждом превращаясь во что-то более структурированное.

```
исходник .asm
   │
   ▼  ① препроцессор   — убрать комментарии, развернуть const/alias/include
текст без «сахара»
   │
   ▼  ② лексер         — разрезать текст на токены (слова)
поток токенов:  [mov] [p0] [acc] [newline] [add] [acc] ...
   │
   ▼  ③ парсер         — собрать токены в структуру (какая инструкция, операнды)
структура (список инструкций / AST)
   │
   ├─▼ ④a эмиттер      — напечатать обратно «ванильный» asm   → это АССЕМБЛЕР
   │
   └─▼ ④b симулятор    — выполнять инструкции по тактам        → это СИМУЛЯТОР
```

В нашем C#-коде эти этапы уже есть, можно подсматривать:
- ① `src/Sio.Assembler/Preprocessor/`
- ② `src/Sio.Assembler/Parse/Tokenizer.cs`
- ③ `src/Sio.Assembler/Parse/Parser.cs`
- ④a `src/Sio.Assembler/Emit/VanillaEmitter.cs`
- ④b `src/Sio.Simulator/`

## 2. Этапы подробнее (с человеческими аналогиями)

### ② Лексер (он же токенизатор)
Берёт строку символов и режет её на **токены** — минимальные осмысленные кусочки.
Аналогия: в предложении «мама мыла раму» лексер выделяет слова `мама`, `мыла`,
`раму`, а пробелы выбрасывает. У нас токены — это мнемоники (`mov`), регистры
(`acc`, `p0`), числа (`100`), метки (`loop:`), перевод строки.

Внутри лексер — это маленький **конечный автомат** (state machine): «вижу букву →
читаю слово; вижу цифру → читаю число; вижу `#` → это комментарий до конца
строки». Ты как раз это пишешь сейчас в IntelliJ-плагине — там та же идея.

📖 [Лексический анализ](https://ru.wikipedia.org/wiki/Лексический_анализ) ·
[en: Lexical analysis](https://en.wikipedia.org/wiki/Lexical_analysis) ·
[Конечный автомат](https://ru.wikipedia.org/wiki/Конечный_автомат)

### ③ Парсер
Берёт **поток токенов** и собирает из них структуру по правилам языка
(**грамматике**). Аналогия: из слов собирает предложение и понимает «кто
подлежащее, кто сказуемое». У нас правило простое и построчное:
`[+/-]? мнемоника операнд*`, либо `метка:`.

Результат парсера обычно называют **AST** (абстрактное синтаксическое дерево).
У нас структура почти плоская (список инструкций), так что «дерево» будет совсем
маленьким — это нормально.

#### Как выглядит наш AST

Файл — это просто список строк, каждая строка — одна из пяти форм:

```
Program
  └── Statement[]  (одна на строку)
        ├── LabelDef    { name: []const u8 }
        ├── Instruction { cond: Cond, mnemonic: []const u8, operands: []Operand }
        ├── Const       { name: []const u8, value: i32 }
        ├── Alias       { name: []const u8, target: []const u8 }
        └── Include     { path: []const u8 }

Cond    = none | true_branch (+) | false_branch (-)
Operand = Register([]const u8) | Immediate(i32) | Label([]const u8)
```

Никакой вложенности, никакой рекурсии — парсер читает строку за строкой и
раскладывает токены в одну из этих структур. В Zig это будет `union(enum)`:

```zig
const Statement = union(enum) {
    label_def:   struct { name: []const u8 },
    instruction: struct { cond: Cond, mnemonic: []const u8, operands: []Operand },
    const_def:   struct { name: []const u8, value: i32 },
    alias_def:   struct { name: []const u8, target: []const u8 },
    include:     struct { path: []const u8 },
};
```

💡 Посмотри на `src/Sio.Assembler/Parse/Statement.cs` — там та же структура на C#,
можно сверяться.

📖 [Синтаксический анализ](https://ru.wikipedia.org/wiki/Синтаксический_анализ) ·
[AST](https://ru.wikipedia.org/wiki/Абстрактное_синтаксическое_дерево) ·
[Recursive descent parser](https://en.wikipedia.org/wiki/Recursive_descent_parser)
(самый простой способ писать парсер руками)

### Условное исполнение: префиксы `+` / `-`
Это «if/else» Shenzhen (единственное ветвление логики, кроме `jmp` по меткам).
Тест-инструкция (`teq`/`tgt`/`tlt`/`tcp`) выставляет внутренний флаг, а дальше:
- строка с `+` выполняется, **только если тест истинный**;
- строка с `-` — **только если ложный**;
- `tcp` включает оба сразу: `+` при A>B, `-` при A<B.

Формально это **предикатное (условное) исполнение**, а не переход: счётчик команд
(PC) никуда не прыгает, инструкция просто выполняется или пропускается.

⚠️ **Важно для лексера:** лексеру семантика не нужна — он лишь **распознаёт
токен**. Но `-` неоднозначен:
- `-` + пробел/буква (`- mov …`) → отдельный токен условия (предлагаю тип
  `CONDITIONAL`), а
- `-` + цифра (`-5`) → часть `NUMBER` (отрицательное число).

Смысл «выполнять или пропустить» реализуется потом — в парсере/симуляторе, не в
лексере. (В `Tokenizer.cs` различение сделано ровно по этому правилу.)

### ① Препроцессор
Работает *до* лексера. Это «найти и заменить» по правилам:
- комментарии (`#`, `;`, `/* */`) → убрать;
- `const MAX 100` → подставить `100` вместо `MAX`;
- `alias LED p0` → подставить `p0` вместо `LED`;
- `include helpers.asm` → вставить содержимое файла.

Аналогия — препроцессор C (`#define`, `#include`).
📖 [Препроцессор](https://ru.wikipedia.org/wiki/Препроцессор)

### Две «прохода» и таблица символов (важно для меток)
Метки (`loop:`) и `jmp loop` создают проблему: когда мы читаем `jmp loop` сверху
вниз, метка `loop` может быть объявлена *ниже*. Классическое решение —
**два прохода**: первый проход собирает все метки в **таблицу символов**
(имя → номер строки), второй — использует её. Это стандартный приём ассемблеров.

📖 [Таблица символов](https://en.wikipedia.org/wiki/Symbol_table) ·
[Two-pass assembler](https://en.wikipedia.org/wiki/Assembly_language#Assembler)

### ④b Симулятор = виртуальная машина
Это «процессор на софте»: есть регистры (`acc`, `dat`), порты (`p0..`, `x0..`),
счётчик команд (PC) и цикл «прочитать инструкцию по PC → выполнить → перейти к
следующей». Наш симулятор ещё и **потактовый** (cycle-accurate): считает, сколько
тактов занимает каждая инструкция — это нужно, чтобы поведение совпадало с игрой.

📖 [Интерпретатор](https://en.wikipedia.org/wiki/Interpreter_(computing)) ·
[Виртуальная машина](https://ru.wikipedia.org/wiki/Виртуальная_машина) ·
[timing-model.md](timing-model.md) (наша модель тактов)

## 3. Главный приём безопасности: дифф против C#

Самое ценное — у нас уже есть **рабочая эталонная реализация** на C#,
проверенная на 483 реальных решениях. Поэтому правило простое:

> На каждом шаге: подаём один и тот же `.asm` в **C#** и в **Zig**, и сравниваем
> вывод. Совпало — шаг готов. Не совпало — баг в Zig-версии.

Это называется **дифференциальное / golden-тестирование**. Не нужно угадывать
«а как правильно» — правильно = «как у C#».

```bash
# пример идеи (псевдо):
./sio assemble examples/us1/extended/main.asm > /tmp/cs.txt        # эталон (C#)
./zig-out/bin/sio assemble examples/us1/extended/main.asm > /tmp/zig.txt
diff /tmp/cs.txt /tmp/zig.txt && echo OK
```

📖 [Golden testing / characterization tests](https://en.wikipedia.org/wiki/Characterization_test)

## 3½. C# — оракул по поведению, но НЕ образец по архитектуре

C# проверен на сотнях решений — **поведение** копируем оттуда. Но устройство
рантайма не копируем: там типичный «enterprise C#», а у нас Zig и можно ниже.

**Что берём как есть (сильные стороны C#):**
- Семантика предикатов: `ConditionalPositiveEnabled` + `ConditionalEqualState`
  (tcp при A==B гасит и `+`, и `-`) — выверено, переносим 1-в-1 (`Tcp.cs`).
- Модель тактов: инструкция возвращает «сколько тактов съела», `slp` = 1 такт
  сам + N тактов сна счётчиком (`Slp.cs`, `StepEngine.Step()`).
- Разделение «шаг» / «лимит тактов» / «трасса» — как *понятия* (не как классы).

**Что в C# слабо — и что делаем по-другому в Zig:**

| C# | Почему плохо | Zig-way (что делаем мы) |
|---|---|---|
| `Decoder.ResolveOperand` парсит **строку операнда на каждом такте** (`int.TryParse`, `ToLowerInvariant`…) | работа парсера в горячем цикле | предекод один раз в `build()` → `union(enum) Operand` ✅ уже сделано |
| Диспетчеризация по **строке** через `InstructionRegistry` + interface `IInstruction` + новый `ExecutionContext` на каждый шаг | hash-lookup, виртуальный вызов и аллокация на такт | `switch (instr.op)` по enum `Mnemonic` — jump table, ноль аллокаций |
| Метки **остаются в потоке инструкций**, `Step()` пропускает их по `IsNullOrEmpty` | метка занимает слот PC и сжигает шаг; PC ≠ номер инструкции | метки выкинуты в `labels`-карту в `build()` ✅ уже сделано. ⚠️ следствие: PC в наших трассах ≠ PC у C# — при диффе трасс сравнивай регистры/IO, не PC |
| `jmp loop` идёт через тот же `ResolveOperand`, метка «резолвится в int» как обычное значение | PC-пространство и значения перемешаны; `mov loop acc` молча сработает | отдельный вид операнда; после `build()` дорезолвить `.label` → индекс инструкции (см. шаг 5.3) |
| Число операндов проверяется **внутри Execute** каждой инструкции, ошибки — исключениями посреди такта | валидация в горячем цикле, и она размазана по 17 файлам | проверить число/виды операндов один раз при `build()`; в горячем цикле — только исполнение |
| XBus: «treat as regular ports» (комментарий прямо в `Decoder.cs`), `slx`/блокировки недоделаны | это вообще не эталон | x-порты делаем по [timing-model.md](timing-model.md) и поведению игры, C# тут не оракул |
| **Два парсера**: `Sio.Assembler/Parse/Parser.cs` и отдельный `Sio.Simulator/Parse/ProgramParser.cs` | дублирование, могут разъехаться | один `Parser.zig` на оба пути ✅ уже сделано |
| `CycleController`, `Tracer` — отдельные инжектируемые классы | церемония ради 1 поля `long` | `cycles: u64` — поле `Machine`; трасса — опциональный writer |

## 4. Пошаговый план (маленькими итерациями)

Идея: каждый шаг — это **что-то, что можно запустить и проверить**. Не пишем всё
сразу. Порядок — от простого к сложному.

### Фаза 0 (разминка): лексер сначала на Kotlin — в IntelliJ-плагине

Прежде чем лезть в незнакомый Zig, **сначала пишем лексер на знакомом Kotlin** —
прямо в IntelliJ-плагине (`editor/intellij-shenzhen-io`). Так мы отделяем две
сложности: «понять, что такое лексер» и «выучить новый язык». Сначала первое — на
языке, который уже знаем.

Почему именно тут удобно учиться:
- **Мгновенная визуальная обратная связь.** Лексер в IDE сразу красит текст —
  написал правило для чисел, перезапустил `gradle runIde`, увидел, что числа
  позеленели. Ошибку видно глазами, без отладочной печати.
- **Каркас уже готов.** В `…/lang/ShenzhenIoLexer.kt` лежит скелет: пробелы и
  комментарии (`#`, `;`) уже разобраны как **рабочие примеры**, а числа / слова
  (инструкции, регистры) / метки — помечены `TODO`. Есть «защита от зависания»:
  непонятный символ съедается по одному, так что бесконечного цикла не будет.
- **Те же понятия, что и в Zig.** Конечный автомат, токены, типы токенов — один
  в один перенесём в Zig на Шаге 1, уже понимая, что делаем.

Чек-лист фазы:
- [ ] Числа → `NUMBER` (опциональный `-`, затем цифры).
- [ ] Слова (буквы/`_`) → классификация: метка (`слово` перед `:`), инструкция
      (см. `Mnemonics`), регистр (`acc`/`dat`/`null`/`p0..p9`/`x0..x9`),
      иначе `IDENTIFIER`.
- [ ] Блочные комментарии `/* … */` → `COMMENT`.
- [ ] Условное исполнение `+`/`-` → отдельный токен `CONDITIONAL` (НЕ путать с
      `-` отрицательного числа: `-` + цифра → `NUMBER`). Подробнее — раздел 2.
- [ ] (по желанию) `@` (init-маркер) как отдельный токен.
- [ ] Проверить в `gradle runIde`: открыть `.asm`, увидеть подсветку.

      sleep_remaining: u32 }. Порядок шага (сверяй со `StepEngine.Step()`):
      PC за границей → стоп; спим → тик сна; предикат не совпал с флагами
      (или equal-state) → PC+1, такт съеден; иначе `switch (instr.op)`.
      Реализовать первые три: `nop`, `mov` (read+write), `jmp` (PC := target).
      Тест: программка из 3 строк, прогнать N шагов, проверить acc и PC.
- [x] **5.5 Арифметика** — `add`/`sub`/`mul` (acc = clamp(acc ± v)), `not`
      (0→100, иначе→0), `dgt`/`dst` (выделить/заменить десятичную цифру —
      смотри `Dgt.cs`/`Dst.cs`, там аккуратные крайние случаи со знаком).
      Это чистые функции — идеальное место для table-driven тестов.
- [x] **5.6 Тесты-предикаты** — `teq`/`tgt`/`tlt` ставят
      `conditional_positive`, сбрасывают equal; `tcp`: A>B → `+`, A<B → `-`,
      A==B → equal-state (оба выключены). Семантику брать из `Tcp.cs` 1-в-1.
      Тест: цепочка `tcp` → `+ mov` / `- mov` на всех трёх исходах.
- [x] **5.7 Такты и `slp`** — `step()` прибавляет к `cycles` сколько съел;
      `slp N`: 1 такт сам + N тактов `sleep_remaining`. `run(limit)` крутит
      `step()` до конца программы / лимита (дефолтный лимит обязателен —
      помним фикс в C#). Тест: точное число тактов на известной программе.
- [x] **5.8 `sio simulate` + `--trace`** — подключить в `main.zig`; трасса:
      такт, PC, инструкция, acc/dat. Дифф против C# `--trace`: ⚠️ наши PC
      сдвинуты (C# держит метки в потоке инструкций) — сравнивать
      последовательность `acc/dat/IO`, не PC.
- [x] **5.9 Порты** — простые `pN`: защёлкнутое значение, read/write,
      clamp 0–100. XBus (`xN`, блокирующие read/write, `slx`) переехал
      в шаг 6.3 — нужен мультичип. ⚠️ C# тут НЕ оракул (см. раздел 3½) —
      опираться на [timing-model.md](timing-model.md).
- [x] **5.10 Недокументированное** — `gen` готов (build-time expansion:
      mov/slp/mov/slp); `@`-init пока парсится без семантики
      (см. [undocumented-instructions.md](undocumented-instructions.md)).

### Шаг 6 — Мультичип: игровая модель времени + Board

Решение (2026-07-02): **совпадаем с игрой по семантике времени** — квант
синхронизации = time unit, а не инструкция. За один time unit чип исполняет
инструкции подряд до `slp`/блокировки; cycles = исполненные инструкции
(метрика мощности), сон циклов не стоит. Подробности и все зафиксированные
решения — в [timing-model.md](timing-model.md) (v2) и доккомментах
`zig/src/simulate/Board.zig` / `Machine.zig`. Варианты координации (lock-step /
event-driven / гибрид) обсуждались 2026-06-22; идём: lock-step → гибридная
перемотка.

Заглушки и красные тесты (6.x) готовы, тела — в mentor-режиме:

- [ ] **6.0 `Machine.runSlice()`** — `Yield` union (`.halted` / `.sleep: u32`),
      `readOperand`/`writeOperand` (порты через `pin_map`/`wires`),
      предохранитель `error.NeverSleeps`. Тесты «6.0 …» в `Machine.zig`.
- [ ] **6.1 `Board`** — `Wire`, `stepTimeUnit()` (машины в порядке индекса,
      записи в провода видны сразу), `run(limit)`. Тесты «6.1 …» в `Board.zig`.
- [ ] **6.2 Чистка** — убить старый `step()`/`sleep_remaining`, вынести
      `ports` из `Cpu` (ветки `.port` из `Cpu.read/write` → `Machine`),
      мигрировать тесты 5.7/5.9/5.10, `sio simulate` → Board с одной машиной.
- [ ] **6.3 XBus** — блокирующие `xN` read/write + `slx`: writer ждёт reader
      и наоборот (честная семантика игры; C# тут не оракул). Новые варианты
      `Yield`: `blocked_read`/`blocked_write`.
- [ ] **6.4 Перемотка** — все спят/заблокированы → `time = min(wake_time)`
      вместо тиканья по одному. Полный event-driven — только если профиль

## 6. Советы новичку

- **Маленькие шаги.** Каждый шаг — запускаемый и проверяемый. Не пиши парсер,
  пока лексер не печатает токены правильно.
- **C# — твой оракул.** Не уверен «как должно быть»? Запусти C# и посмотри.
- **Сначала корректность, потом красота.** Пусть первый Zig-код будет «уродливым,
  но рабочим». Перепишешь, когда поймёшь язык.
- **Тесты с первого дня.** Дифф против C# = почти бесплатные тесты.
- **Не лезь сразу в оптимизации/аллокаторы.** Сначала пусть просто работает.
